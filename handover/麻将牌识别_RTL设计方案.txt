================================================================================
第 0 节  一句话
================================================================================
在【不用 CNN、不占 DSP、不碰 HDMI 时序域】的前提下，用
   帧差定位（已有）+ 颜色分组 + 子图计数 + 几何 + 灰度 SAD 模板匹配
实现对麻将牌的多目标识别。

模板库已生成：33 类、统一 32x32 8 位灰度、264 Kbit（14 块 ERAM20K），
可分性经实测验证（见第 3 节）。

★ 与"识别"无关但同样重要的一条：识别逻辑**不得**加进 clk5/clk2 域 ——
  刚把 clk5 从 -0.049 收敛到 +0.023ns（交接文档第 9 节），加负载会前功尽弃。


================================================================================
第 1 节  硬性约束
================================================================================
1. 不用 CNN、不用需要大量乘加的结构（器件只有 40 个 DSP）。
2. 不改显示时序参数（AGENTS.md 规则 3）。
3. 新模块必须【内联】进 design_top_wrapper.v（规则 1：不往 td_project/*.al 加文件，
   那里会被 TD 用内存里的文件列表覆盖）。
4. ★ 时序红线（见第 4 节的数据）：
       clk5 HDMI_SERIAL 750MHz = +0.023ns  ← 只剩 23 皮秒，一个字节都不许加
       clk2 HDMI_PIXEL  150MHz = +0.414ns
       clk0 MIPI_RX     120MHz = -0.990ns  ← 只影响画质，识别逻辑全放这里
   跨域只传 8 个字节的牌 ID（复用 hdmi_mixer 已有的跨域坐标机制）。
5. 复用已有资产：frame_diff_onchip 的 bbox 输出、hdmi_mixer 的跨域查询、
   osd_char_lib 字库。

第 3 节  数据结论（模板可分性实测，三条都很关键）
================================================================================
用 FluffyStuff 的 CC0 牌面跑工具链实测（平均绝对差 MAD，0..255，越小越难分）：

【结论 1】最难分的对，正好是"数子图"能一刀切开的
   最终方案下组内最像的 6 对：
       四筒 vs 五筒   15.99   ← 全场最难，但 F3 数圆：4 vs 5
       七索 vs 九索   22.98   ← F3 数竹：7 vs 9
       五索 vs 六索   23.46   ← F3 数竹：5 vs 6
       六筒 vs 八筒   31.22   ← F3 数圆：6 vs 8
       中   vs 東     33.09   ← 只能靠模板
       五索 vs 八索   35.16   ← F3
   → F3（子图计数）不是可选优化，是**必需**：它把最难的 18 类（筒+条）从
     模板匹配里整个拿掉。

【结论 2】万子的形近字靠"提高分辨率"救不了，靠"只取上半部"能救
   同一批万子牌，两种做法的实测对比：
       对            48x48 全牌    32x32 全牌    32x32 取上半 55%
       二萬 vs 八萬     18.78         18.16          39.9   ← 翻倍
       三萬 vs 五萬     18.19         20.11          47.3   ← 翻倍
   原因：万子的差异只在**上半部的数字**，下半部的"萬"字所有万子都一样，
        把整张牌拿来比，"萬"字的相同部分把差异稀释掉了。
   ★ 顺带结论：裁剪后 32x32 反而**优于** 48x48 全牌，而且省一半内存。
   ★ 但【字牌不能裁】：中/發/東/北 是居中的单个字，裁上半会切掉字形
     （实测 35% 裁剪时"發 vs 北"从 27.3 掉到 14.6）。

【结论 3】白板（白）是"没有图案"的牌，模板对它没有区分力
   类 Haku 前景占比 0.0%（预览图确认整张全白）。
   它跟任何空白模板的距离都极小 → 必然误判。
   → 白板【不进模板库】，改用规则：前景占比 < 2% → 判为白板。
     与 F4（填充率）共用一套逻辑，顺带省一类。

决策顺序（用最便宜的先把搜索空间砍掉）：

   4) 万/字组：F5 SAD 取最近邻；距离 > 阈值 → 判"未知"（不硬猜）

第 6 节  模板库规格（已生成）
================================================================================
【规格】
  统一 32x32、8 位灰度，33 类（白板不入库）
  万子（Man1-9）预处理时只取**内容框的上半 55%**（数字区），其余用全牌
  对比度拉伸：按 1%~99% 分位映射到 0..255（抗离群点）
  二值版（1 位/像素）另行给出，供 TB 与退路使用

【类号表】（RTL 用区间就能判组）
   类 0      = 未知/拒识
   类 1~9    = 一筒~九筒        （Pin1~Pin9）
   类 10~18  = 一索~九索        （Sou1~Sou9）
   类 19~27  = 一萬~九萬        （Man1~Man9）
   类 28~31  = 東 南 西 北      （Ton Nan Shaa Pei）
   类 32~33  = 中 發            （Chun Hatsu）
   类 34     = 白（Haku）—— 不在库内，由"空白率<2%"规则判定

【生成的模块与接口】（在 sim/out/tile_tmpl_pkg.v 里）
   module tile_tmpl_rom_g32_gray( I_clk, I_addr[13:0], O_data[31:0] );
       地址 = (cls-1)*256 + row*8 + word，每字 4 个 8 位像素（高位在前）
   module tile_tmpl_rom_g32_bin ( I_clk, I_addr[10:0], O_data[31:0] );
       地址 = (cls-1)*32 + row，每字一行（MSB=最左像素）
   module tile_color_tbl( I_cls[7:0], O_sig[31:0] );
       4 桶(红/绿/蓝/无彩)各 8 位
  两个 ROM 都是"reg 数组 + 同步读"的推断式写法（与工程现有风格一致）。

【ROM 初始化：两个方案，建议先用 A】
  A. 内联 initial ROM（当前生成的就是这种）
     · 不依赖文件路径解析，上电即用，零外部依赖
     · 代价：tile_tmpl_pkg.v 约 306 KB（≈9600 行）；内联进 design_top_wrapper.v
       会让该文件变长，TD 综合时间增加但可用
  B. $readmemh + .mem 文件
     · 工程里已有先例：ph1p_ddrphy_init.v 用 $readmemh(ROM_INIT, ...)，
       但那个路径是 TD 的 IP 流程用参数灌进去的
     · 自建模块要硬编码相对路径，TD 里基准目录不确定 → 需要先做一次
       2 分钟的综合实验验证路径解析，再决定
  C.（以后）UART 在线灌模板，照 ralbertazzi 的 template_injector
     · 好处：换牌/换光照重标定不用重新综合 —— 这正是"用自己的牌校准"的正道
     · 代价：加 UART 接收 + 装载 FSM（约 300 LUT），且掉电丢失需重灌

【资源】灰度库 264.0 Kbit → 14 块 ERAM20K（108 块里 13%）；二值库 33.0 Kbit → 2 块

【素材来源与替换】
  当前模板来自 FluffyStuff/riichi-mahjong-tiles（CC0 公有领域），日麻与中式
  牌面一致。但**美术风格与你手上的实体牌不同**，实物识别前建议用自己的牌重标定：
      把自己的 34 张牌各拍一张 → 放进一个文件夹 → 重跑工具链
      命令：python sim/make_tile_templates.py <你的素材目录> sim/out "<方案>" "Haku" "<类序>"

  阶段 4  decide 决策树 + 接进 hdmi_mixer 画牌名

第 9 节  工具链用法
================================================================================
  python sim/make_tile_templates.py [素材目录] [输出目录] [方案] [排除] [类序]

  方案格式： "32:55=Man*;32=Ton,Nan,Shaa,Pei,Chun,Hatsu,Pin*,Sou*"
             —— "边长[:垂直裁剪百分比]=通配符列表"；未匹配到的用最后一组
  排除：     "Haku"（白板这类无图案的牌不进库）
  类序：     逗号分隔的类名，决定类号顺序（便于 RTL 用区间判组）
  本次实际使用的完整命令：
    python sim/make_tile_templates.py sim/_tmp/tiles_src sim/out \
      "32:55=Man*;32=Ton,Nan,Shaa,Pei,Chun,Hatsu,Pin*,Sou*" "Haku" \
      "Pin1,...,Pin9,Sou1,...,Sou9,Man1,...,Man9,Ton,Nan,Shaa,Pei,Chun,Hatsu,Haku"

第 10 节  未决问题与风险
================================================================================
1. 【最大风险】模板来自 CC0 矢量牌面，**与实体牌美术风格不同**。
   实物识别前必须用自己的牌重标定（工具链支持，见第 6 节）。
   若实物牌风格差异大，32x32 可能不够 → 退回 48x48（库变 31 块 ERAM）。
2. 光照：模板匹配对亮度/对比度敏感。contrast_norm 是必需级，不是可选级
   （fengs2021 的 stretchContrast 就是为这个）。建议加"每次校准时的均值/
   方差归一化"，或在 F5 前做 min-max 拉伸。
3. 遮挡/叠牌：本方案假设每张牌大致完整可见。若牌会相互遮挡，
   F3 数子图会漏计、SAD 会偏大 → 靠"距离 > 阈值判未知"兜住，不硬猜。
4. 8x8 块粒度对 F3 的影响：细竹条可能被切碎或被邻块粘住。
   阶段 2 的 TB 必须覆盖这两种边界；必要时把局部位图细化到 4x4 块
   （位图从 8 字涨到 32 字/槽，每槽 ERAM 0.5Kbit，仍可接受）。
5. bbox 来源假设：识别沿用 frame_diff 的 bbox。若牌不动（静止摆放），
   帧差法没有输出 → 需要"静态场景也出框"的机制（例如按 SW 强制用
   固定格网扫描，或改用基于边缘/颜色的静态分割）。★ 这一点要先跟用户确认
   使用场景：是"牌被移动时识别"还是"静止摆放也要识别"。
6. ERAM 用量：模板库 14 块 + 各模块 ~3 块 = 17 块左右。
   当前工程已用多少 ERAM 未统计，实施前应先看一次综合报告的资源表。

第 11 节  OSD 显示格式（阶段 1 上板验证用）
================================================================================
hdmi_mixer 左上角的文本块由 4 行扩到 7 行，新增 3 行显示识别特征。
原来的 4 行不变：

    H xxxx   KEY4 计数值            （十进制 BCD）
    D xxxx   左右边界距离           （十进制 BCD）
    F xxxx   帧差帧数               （十进制 BCD，拨上 SW4 后必须一直涨）
    M xxxx   上一帧运动块数          （十进制 BCD）
    ---------------------------------------------------------------
    N xxxx   ★ 选中槽的前景像素数      （**十六进制**）
    C xxxx   ★ 选中槽的颜色签名        （**十六进制**）
               4 个字符 = 红/绿/蓝/无彩 四个桶，各取高 4 位（即 值>>4）
    A xxxx   ★ 槽号 / 标志 / 有效槽数   （**十六进制**）
               字符1 = 当前显示的槽号 0..7
               字符2 = 标志位：bit0=该槽有效  bit1=判为白板(空白率<2%)
                                bit2=宽高比通过(0.708±15%)
               字符3,4 = 本帧有效槽总数 00..08

  ★ 槽号选择：自动轮播槽 0..7，每个约 1.5 秒
      SW2 拨上 = 冻结轮播（停在当前槽，方便读数）
      SW3 拨上 = 只轮播有效槽（跳过空槽）
    （这两个开关原来是"算法观测点选择"，早已从 ISP 断开成死代码，故借用）

  读法举例：屏幕上 `A 3502` 表示
      当前看的是槽 3、标志 = 0b101 = 有效 + 宽高比通过（不是白板）、全帧共 2 个有效槽；
      `N 04D2` = 该槽前景 1234 个像素；`C 9016` = 红桶≈144、绿 0、蓝≈16~31、无彩≈96~111。

  ★ 怎么用它判断标定对不对：
     1) ROI 门控对不对：把 N 和该槽 bbox 的像素面积比一下。牌完整落在框内时，
        前景占比大致等于"牌面花纹占牌面的比例"（数牌约 15%~40%）。
        如果 N 小得离谱 -> 门控没对上（改 tile_recog_onchip 的 GXOFF/GYOFF）
     2) 颜色分组对不对：筒/条/万/字的签名差别很大。若四个桶几乎一样 -> 
        Y_DARK / SAT_THR 需要按实拍重新标定
     3) 白板：真白板应显示 bit1=1；若花纹牌也报白板 -> BLANK_NUM 太大或 N 太小
     4) 宽高比：立牌应 bit2=1；若为 0 -> 实测框的宽高比，改 tile_recog_onchip.v 里
        的 12/17 判据（`s_w17` / `s_h10` / `s_h14` 那三行，纯移位加法）

第 12 节  ★ 上板前已经踩过的两个坑（2026-10-14）
================================================================================
【坑 1】DSP 上限 —— 算术 * 和"复活死逻辑"都会吃 DSP（这条最贵，直接让布局失败）

  基线（本次识别改动之前）：LUT 14261 / FF 17266 / DSP **33**；器件上限 40，
  **只剩 7 个余量**。

  (a) 我在识别模块里写了 6 个 `*`，其中还有"乘以常量"。Verilog 里 `*` 常量
      **不等于**移位，是综合器决定的 —— TD 把它们全映射成 DSP，推到 49~54，
      布局器报：
          PHY-7027 CRITICAL-WARNING: model type (DSP) exceed the design limits
          PHY-9002 ERROR: Placer initialization failed. ... PHY-9146, PHY-9147, PHY-9179
      （TD 提示的三个码是陪衬，真根因在 7027）

  (b) 更隐蔽的一个：为了拿颜色信息，我把 ISP 的 `s1_cb/s1_cr` 引出。结果
      `rgb_to_ycbcr_4` 里 **24 个常量乘法器从"死逻辑"复活** —— 原来只有 Y 被引出，
      Cb/Cr 那两路被优化掉了。`u_isp_top/u_sobel` 的 DSP 从 12 涨到 28。

  ➜ 解决办法（两条都要做）：
     ① 所有定标乘法手写移位加法；连"变量×变量"也去掉 —— bbox 面积不再用 w*h，
        改成**块计数器**逐块累加（顺带更准：它统计的是真正被门控到的块数）。
        ★ 注意 TD 仍可能把"移位加法"重新识别成常量乘法，所以能不用就不用。
     ② 色彩信息改成引出 **`O_col4`**：色系码（0红1绿2蓝3无彩），用 max/min +
        比较器算，**零乘法**，端口也从 64 位降到 8 位。判据与离线模板工具链
        `make_tile_templates.py` 的 `color_sig` **完全一致**（max-min < 40 判无彩）。

  ➜ 验证结果（真实综合，不是估算）：**#DSPs = 33，与基线完全一致**，
     识别模块贡献 0；u_sobel 回到 12。

  ➜ 定位工具：`python sim/dsp_by_module.py <门级网表>` —— 按模块列出 DSP 分布，
     一眼看出超限是谁造成的。
  ➜ 只跑综合的验证方法（约 3 分钟，值得在每次改动后跑）：
     在 td_project/camera_to_dsi_display_Runs/ 下建一个目录，放 settings.cfg
     （end_step 改成 opt_gate）、flow_syn_tu.tcl、camera_to_dsi_display.prj，
     **把进程工作目录切到该目录**（否则 ./settings.cfg 找不到），然后
         set start_step read_design
         source {<绝对路径>/flow_syn_tu.tcl}
     喂给 `D:\anlogic TD\bin\td_commands_prompt.exe` 的标准输入。

【坑 2】给"内联副本"加端口 —— 必须改源文件，否则 TD 报 cannot find port
  `isp_top.v` 第 676 行起是 `sobel_edge_128` 的内联副本；我当初把 Cb/Cr 端口
  加在了副本上，漏了源文件 `isp/sobel_edge_128.v` 和包装层 `module isp_top`。
  ➜ 规则：加/改端口改**源文件** -> 跑 inline 脚本 -> 跑 `sim/check_ports.py`。
  ➜ 校验方法的教训：不要用"关键词过滤编译输出"来判断有没有错（我那次过滤词里
     没有 `O_cb_out`，错误被滤掉了）。判据应该是"**非 Unknown module 的错误必须为零**"。


【坑 3】bbox 的单位是【像素】不是块 —— 上板现象：N 基本 0、偶尔 FFFF、C 全 0
  frame_diff_onchip.v 第 464-468 行写得很清楚：
      //  候选的像素坐标 = 块坐标 << 3
      wire [11:0] c_x1 = {4'd0, t_x1[s_scan][7:0]} << 3;
      wire [11:0] c_x2 = ({4'd0, t_x2[s_scan][7:0]} << 3) + 12'd7;
  （12 位宽本身就暗示是像素：块坐标 0..239 只要 8 位）
  我按块坐标去比较 -> 拿"块列 0..239"比"像素 800..928"：
      · 基本永不命中           -> N = 0000、valid = 0、C = 0000
      · 偶尔低位碰巧落进范围   -> 一个槽狂吞像素 -> N 饱和成 FFFF
      · A 行高位仍在递增       -> 槽号轮播是好的（那部分没问题）
  ➜ 修法：取 12 位里的 `[10:3]` 就是块号（x2 = 块<<3+7，右移 3 位正好还原；低 3 位是块内偏移）。
  ➜ 判读现象的经验：**"框画对了但特征全 0"** 优先怀疑坐标单位/相位对不上，
     而不是怀疑特征算法本身。
  ➜ 可能残留半块相位差（frame_diff 的块计数相位与本模块独立重建的相位可能差半块）：
     若上板看到 N 明显偏小（只覆盖到牌的一部分），用 tile_recog_onchip 的
     GXOFF/GYOFF 各调 ±1（单位 = 块）。
