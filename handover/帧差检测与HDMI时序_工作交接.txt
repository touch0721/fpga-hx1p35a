第 2 节  本会话做了什么（时间顺序）
================================================================================
【A. 帧差法多目标检测】★ 核心成果
  需求演进：
    1) 最初是"上一帧 vs 这一帧"的帧差 -> 改成"背景帧 vs 这一帧"
       - KEY4 按下 = 持续抓取背景（不报运动）
       - KEY4 再按 = 冻结背景，开始检测
    2) 原来用"列投影 + 行投影"只能出一个外接矩形，两个物体会被并成一个大框
    3) 先试了【行游程匹配（连通域）】，能用但需要一张 240x135 的运动位图
       （2 块 ERAM），而且邻域判定只用 x，垂直重叠的物体分不开
    4) ★ 最终采用用户提出的【邻域投票法】：
       - 每个运动块对 16 个目标槽各投一票
       - 槽无效 或 该块落在槽的邻域之外 -> 投"新目标"票
       - 全票 -> 新建目标；部分票 -> 扩展那些"没投票"的目标的 bbox
       - ★ 邻域判定同时用 x 和 y，所以上下分开、左右重叠的物体也能分开
       - 不需要运动位图，省掉 2 块 ERAM
    5) 投票前加了【3x3 开运算（先腐蚀后膨胀）】去孤立噪点
    6) 加了【输出框重叠合并】：本帧候选框与已输出框重叠就并入，不新开框
    7) NT 16 -> 32（放第 4 个物体时目标表被占满 -> 全部不识别）
    8) MAXO 4 -> 8（原来只是随手取的默认值，无硬件理由）

【B. SW1 改用途：显示帧差二值图】
  - SW1 原功能（Sobel 边缘图 + 红色边界）已悬空：isp_top 的
    I_sobel_en 和 I_bnd_en 都固定接 1'b0
  - SW1 拨上 = 显示帧差二值图（白 = 该 8x8 块在动，黑 = 静止）
  - ★ 关键教训：一开始做成"与像素流同拍输出"，结果横条纹+频闪
    原因：帧差模块跑在【ISP 输出】时序，mixer 跑在【HDMI 显示】时序，
          两者差整整一帧，流被当成当前帧的图用 -> 错位
    修法：帧差模块把运动位存成 240x135 位图（32 位打包，1080 字 ≈ 2 块 ERAM），
          mixer 用 S_x_1d/S_y_1d 发地址查询，读出的字正好与 S_x_2d 对齐

【C. HDMI 显示时序 —— 有改动也有回退，务必看清】
  1) 实测：原来 H_FrameSize=2223 + 像素时钟 150 MHz = 59.979 Hz（近似 60）
  2) 我改成 2222（60.006 Hz）-> ★ 屏幕无显示 ✗ -> 已回退到 2223
     ★ 教训：显示时序参数不是"算出来更好就能改"，动了就可能黑屏
  3) PLL 硬约束（user_source/ip_source/PLL/PLL.v）：
        参考时钟 FIN = 50 MHz，VCO = 1500 MHz
        CLKC0_DIV=15 -> 100.000 MHz 系统时钟
        CLKC1_DIV=63 ->  23.81 MHz 摄像头
        CLKC4_DIV=10 -> 150.000 MHz HDMI 像素
        CLKC5_DIV=2  -> 750.000 MHz TMDS 串行（= 像素 x5）
     ★ 148.5 MHz 分不出来：1500/148.5 = 10.101 非整数
       而且 TMDS 要 742.5 = 148.5x5，所以 VCO 必须同时被两者整除
       VCO = 1485j，而 1485/50 = 29.7 非整数 -> ★ 50 MHz 参考下无解
       （穷举验证过 VCO <= 1600 MHz 内没有任何可行解）
     ➜ 想严格 60.000000 Hz 只能靠 TD 的 PLL IP 开小数分频（PI_FRAC_EN），
       那是 GUI 操作，需要用户生成 IP

第 5 节  待办 / 未解决问题
================================================================================
【★ 最优先：clk5 余量】
  上一版（退回后的源码）实测 clk5 = +0.008 ns ✓
  但同一份 RTL 重跑综合可能又变负（布局波动，只有 35 个端点）
  做法：
    1) 重新综合 -> 看 clk5
    2) 若为负 -> TD 里提高布局布线优化等级
       （Optimization Effort -> High/Highest，打开 Multi-pass / Physical Synthesis）
    3) 仍为负 -> 重跑几次挑最好的一次（换 seed）
  ★ clk5 违规 = 显示器右上角弹 "HDMI" 重新握手 = 偶尔断联（用户实测现象）
  ★ 不能从 RTL 修：lane_lvds_10_1.v 里给 I_data_in 加寄存会推迟 TMDS 加载时刻
     1 个串行时钟，load_en 每 5 个串行时钟才有效一次 -> 位序全错 -> 画面废

【clk0 = -1.629 ns（105 条违规）】
  在 MIPI 接收 + ISP 前端域。只影响画质（偶发噪点），不影响 HDMI 锁屏。
  修它要动 ISP 流水线结构，工作量大风险高。建议靠提高 P&R 优化等级压。

【白色测试框】
  mixer 里 TBOX_X1=100/TBOX_X2=399/TBOX_Y1=100/TBOX_Y2=199，
  由 I_tbox_en（=SW4）控制。多目标功能已验证可用，建议去掉。

【clk2 的 -0.144 ns】
  我修的两次（b8e3edd / 2c1e0f6）能把它变正，但会让 clk5 变差（布局效应）。
  如果重新综合后 clk2 仍然负且 clk5 为正，可以考虑只重新应用 b8e3edd（mbox_hit 流水线）。

【跨帧跟踪（可选增强）】
  现在目标表每帧清空、按扫描顺序分配槽位。若某帧漏检一个物体，
  后面物体的槽位会整体前移 -> 框跳到别的物体位置 -> 看起来像闪烁。
  HOLD_FRM 治不了这个（它只能"保持"，认不出是不是同一个物体）。
  根治办法：让本帧目标去匹配上一帧的框（中心距离 / 重叠面积），沿用槽位。

第 6 节  踩过的坑（★ 新对话务必先看，避免重复）

【1】位宽截断 —— 本会话最坑的一类
  · s_fo 只有 2 位 -> 第 4 个框时 3+1 回绕成 0
    -> O_obj_cnt 显示 0，且 FO_DONE 里 "qi >= s_fo" 把所有框都清掉 -> 频闪
  · s_hold 只有 2 位 -> HOLD_FRM=8 被 [1:0] 截断成 0 -> 防闪烁完全没生效
    （我白让用户上板验证了两轮才发现）
  · s_scan/s_sel 在 NT 从 16 改 32 后仍是 5 位 -> 扫描不终止 -> 重复出框
  ➜ ★ 改任何参数后，立刻核对承载它的寄存器位宽是否够

【2】always 块内被写的 reg，用组合逻辑读会拿到【旧值】
  · 重叠合并判定原本用 O_bv[gk]，但 O_bv 在同一 always 块里被写
    -> 读到上一帧的框 -> 本帧第一个候选就"重叠" -> 全被吞掉
  · 修法：用独立的 s_emit 掩码（进入扫描时清零）
  · 同类问题在本项目已出现 3 次

【3】无符号数做减法得到负数 -> 比较恒真
  · 邻域判定写成 (bx < t_x1[vi] - MARGIN)
    t_x1 是 reg[9:0]，MARGIN 是 integer(32 位有符号)
    0-2 = -2 -> 按 32 位无符号解释 = 4294967294 -> 判定恒真
    -> 所有目标都投"新目标"票 -> 每个块都新建目标
  · 修法：写成全加法形式 (bx + MARGIN >= x1) && (bx <= x2 + MARGIN)

【4】变量索引的非阻塞赋值
  实测 iverilog 下 t_val[t_cnt] <= 1'b1 没写进去（也可能是别的原因）
  改成显式 for 循环按 t_cnt 命中写入后正常。

第 9 节  【2026-10-12 追加】clk5 时序收敛 —— 已解决，零 RTL 改动
================================================================================
【一句话】HDMI 链路的时序违规全部清零，第 5 节那个"最优先：clk5 余量"已完成。

【根因】lane_lvds_10_1.v 的 4 个实例（hdmi_phy_warpper.v 里 u0..u3）内部的
  S_odd_even / S_load_en 三条链是纯自由计数器、与数据无关，4 份完全相同。
  TD 综合时按"等价逻辑合并"把它们并成了 1 个寄存器，于是那条
  S_load_en_2d 网要驱动 4 个 lane × 10 个移位寄存器：
      综合后扇出 = 40（每 lane 各一份时应为 10）
      布线后该 net 延迟 0.552ns，占 clk5 最差路径的 50% → clk5 = -0.049ns
  ★ 物理阶段修不了它。试过 phys_opt -force_replication_on_nets 定向复制：
    扇出 19→15，但 net 延迟一个皮秒都没变（瓶颈是驱动器离负载太远，不是负载
    数量）。这条路可以不用再试。

【修法】两条参数，RTL 一行没改：
  1) 综合 syn_1 ： set_param rtl merge_equal off
     官方说明（td.exe 内）："Merge equivalent logic. on: merge equivalent
     logic and save area resources. off: preserve equivalent logic."
     效果：那条网扇出 40 → 10；综合级 clk5 从 -0.473 改善到 -0.262。
     代价：资源几乎不变（u_uicfgcs520 181→173 LUT，video_out 192→191）。
  2) 布局布线 phy_1 ：TimingUltra 全部 14 条参数
     效果：clk2 仅靠这一项就自己转正（-0.356 → +0.059）。
