### 1.1 文件与编译状态

```
│   ├── uics520reg.v                 ← 备用全尺寸表（.al AutoExcluded）
│   └── uics520reg_full_2560x1920_30.v ← 备用表（.al AutoExcluded）

```

> 说明：`uics500_cfg/*` 除 `uii2c.v` 外全部 `AutoExcluded=true`，属历史遗留死代码，本轮未改动。
> 端口与模块名保持原样，因此 `design_top_wrapper.v` 的例化名与 `.al` 文件列表**无需变动**。

### 1.2 数据通路

```
design_top_wrapper.u_uicfgcs520
        │  24 MHz(I_clk) ── I2C SCL/SDA ──> 摄像头
        │
        ├── 读 0x3107/0x3108 校验 Sensor ID
        ├── O_cfg_done ──> ST_IDLE 之后逐条写 uics520reg_720p60
        └── I_ae_req  ──> 逐条写 uics520regAE（曝光 + 增益）
                              ▲
                              └── SC520GainTbl（I_ag 16..176 → {0x3e08,0x3e09}）
```

每笔 I2C 写 = 4 字节：`[CAM_ID][reg_hi][reg_lo][data]`，8 bit 寄存器数据、16 bit 寄存器地址（与 INI 头部
`mode=3: Stmicro 16Addr,8Data` 一致）。

### 1.3 状态机（改动后）

| 状态 | 作用 |
| --- | --- |
| `ST_IDH_REQ/BUSY/DONE`、`ST_IDL_REQ/BUSY/DONE` | 随机读 `0x3107`、`0x3108` |
| `ST_CHECK_ID` | **ID == 0xEE27 才继续**（SC500CS 表 1-6），否则 `ST_ERROR` |
| `ST_IDLE` | 未配置完→写初始化表；配置完→响应 `I_ae_req` 写 AE 表 |
| `ST_WR_REQ/BUSY/DONE` | 单条寄存器写 |
| `ST_RESET_WAIT` | 写完索引 0（`0x0103` 软复位）后等 **5 ms** |
| `ST_STREAM_WAIT` | 写完索引 115（`0x0100=0x01` stream on）后等 **10 ms** ← **本轮新增** |

## 2. 适配依据

### 2.1 数据手册 V1.8 确认的关键语义

| 功能 | 地址 | 手册出处 | 取值/结论 |
| --- | --- | --- | --- |
| I2C 从机地址 | SID 引脚 | 表 1-4 | SID 低→`7'h36`→8bit 写地址 **0x6C**（与现有 `CAM_ID` 一致，未改） |
| Sensor ID | `0x3107`/`0x3108` | 表 1-6 | 默认 `0xee`/`0x27` → **0xEE27** ← 本轮关键修正 |
| 软复位 | `0x0103[0]` | 表 1-3 | 写 1 复位 |
| 软睡眠 / 流开关 | `0x0100[0]` | 表 1-2 | 0=睡眠，1=stream on |
| MIPI lane / 位宽 / PHY | `0x3018`/`0x3031`/`0x3037` | 表 1-9 | 默认即 2-lane / raw10 / 16-bit，无需写 |
| 输出窗口 | `{0x3208,09}` 宽 / `{0x320a,0b}` 高 | 表 2-8 | 本次写入 1280 / 720 |
| 帧长 VTS | `{0x326d[6:0],0x320e,0x320f}` | 表 2-9 | 本次写入 1000 → 60 fps |
| 曝光 | `{0x3e20[3:0],0x3e00,0x3e01,0x3e02[7:4]}` | 表 2-2 | 单位 1/2 行，最大 `2*VTS-10 = 1990` |
| ANA GAIN / ANA FINE GAIN | `0x3e08` / `0x3e09` | 表 2-3、2-4 | 粗调 ∈{0x03,0x07,0x0f,0x1f}，细调 ∈0x20~0x3f，最大 15.750x |
| DIG GAIN / DIG FINE GAIN | `0x3e06` / `0x3e07` | 表 2-5 | `0x00`/`0x80` = 1.000x |
| **AGC 使能** | `0x3e03[3:0]` | 2.2.3 节 | 必须置 `4'hb`，否则上述增益寄存器不生效 |
| HD 模式定义 | — | 表 1-7 | 1280x720@60 = 2x2 binning + crop |
| 镜像/倒置、测试图 | `0x3221`、`0x4501` | 表 2-7、2-10 | 均不写 = 关闭 |

### 2.3 关于你提供的 INI：判定为非 SC500CS 配置

文件名 `cleaned_0x30_eco2_8bit_2lane_mipi_27Minput_388.8Mbps_20170928_130gs_1280x1024_60fps_8.4Kfuwell_aec_62Xgain.ini`
（96 项）。与 SC500CS 各权威表逐条比对结果：

| 证据 | 数据 |
| --- | --- |
| 地址交集 | 与 SC500CS 各表交集仅 **29 个**（SC500CS 表有 113~118 个地址） |
| 取值一致 | 交集中**同值仅 4~6 个**（`0x0103`、`0x3202`、`0x3213` 等） |
| I2C 从机地址 | INI 头部 `SlaveID=0x60`（7'h30）；手册表 1-4 只定义 `7'h36`/`7'h10` |
| 窗口/时序自相矛盾 | 按 SC500CS 语义：高 `{0x320a,0x320b}=0x0400`=1024，但 VTS `{0x320e,0x320f}=0x021c`=540 < 1024，物理上不可能（`0x320c/d`=HTS、`0x320e/f`=VTS 已由手册表 2-9 固化） |
| 独有寄存器块 | INI 的 `0x3030~0x303f`、`0x3380~0x3384`、`0x3518/19`、`0x3d08`、`0x3f08`、`0x5b00~0x5b03` 在 SC500CS 全部权威表中**均不存在** |
| 模式不符 | INI `0x3031=0x08` = RAW8；本工程 FPGA ISP 通路（`raw10_unpacket_2lane` 等）为 RAW10 |
| 输入时钟不符 | INI 为 27 MHz；本工程 PLL 给摄像头的是 **24 MHz**，与原厂 720p60 表一致 |

**因此该 INI 不能作为取值来源**：从机地址、窗口/VTS、像素格式、时钟全都对不上，按值搬迁会导致
Sensor 无输出。其可用价值仅限于两点，本轮已采纳/已覆盖：

1. `0x3e03 = 0x0b`（AGC 使能）——与手册 2.2.3 节要求一致，**已并入新初始化表**（原厂 720p60 表未写此项）。
2. 序列结构 `0x0103=1 → 0x0100=0 → … → 0x0100=1`——原厂 SC500CS 720p60 表本身即为此结构，已满足。

### 2.4 相对原厂表的唯一新增

| 索引 | 寄存器 | 值 | 依据 |
| --- | --- | --- | --- |
| 112 | `0x3e03` | `0x0b` | 手册 2.2.3 明文要求；INI `0x3e03,0x0b` 佐证；置于 `0x3e08/0x3e09` 增益写入**之前**，确保增益生效 |

除此之外，新表与官方 SC500CS 原厂 720p60 表**逐条完全相同**（脚本已断言）。

## 4. 分辨率 / 帧率不变式（证明）

| 寄存器 | 含义 | SC520CS（改前） | SC500CS（改后） | 判定 |
| --- | --- | --- | --- | --- |
| `0x3208`,`0x3209` | 输出窗口宽 | `0x05`,`0x00` = 1280 | `0x05`,`0x00` = **1280** | ✅ 相同 |
| `0x320a`,`0x320b` | 输出窗口高 | `0x02`,`0xd0` = 720 | `0x02`,`0xd0` = **720** | ✅ 相同 |
| `0x320e`,`0x320f` | VTS 帧长 | `0x03`,`0xe8` = 1000 | `0x03`,`0xe8` = **1000** | ✅ 相同 |
| `0x0100` | stream on | `0x01` | `0x01` | ✅ 相同 |

- VTS=1000 且帧率 60 fps ⇒ 行时间 = 1/(60×1000) = **16.667 µs**（改前改后一致）
- 曝光上限 `2*VTS-10 = 1990` 不变 ⇒ `ae_set.v` 无需调整
- 窗口起始 `0x3210/11`、`0x3212/13` 由 `0x000a`/`0x0004` 变为 `0x0002`/`0x0002`——**属原厂该模式的
  固有裁剪起点，不改变输出尺寸**
- FPGA 侧检查项 `S_csi_data_length == 16'h0320`、`S_mipi_line_count == 720` 只依赖分辨率与 RAW10，
  两种模式的行字节数都是 1280×10/8 = 1600 B，**无需改动**

## 5. MIPI 链路速率：828 → 480 Mbps/Lane

SC500CS 原厂 720p60 表的 `0x320c/0x320d = 0x0640 = 1600`（HTS），表内注释亦写明 `480 Mbps/lane`
（`0x4837=0x42`）：

```
像素时钟 = HTS × VTS × fps = 1600 × 1000 × 60 = 96.0 MHz
Lane 速率 = 96 MHz × 10bit ÷ 2 lane = 480 Mbps/Lane
MIPI 时钟（DDR）= 240 MHz → 周期 4.1667 ns
```

原工程按 SC520CS 的 828 Mbps/Lane 配置（`period 2.415 ns` = 414.1 MHz DDR），因此本轮同步调整了：

1. `.sdc` 的 `mipi_rx_ck_pad` period（§3.6）
2. `design_top_wrapper.v` 的接收均衡/VGA 增益（§3.5）

**未受影响**：PLL 输出（`S_24m_clk` 仍为 24 MHz，SC500CS EXTCLK 范围 6~40 MHz 内）、
`LANE_NUM=2`、`BYTE_NUM=1`、ISP/HDMI/DDR 全部通路。

## 6. 验证方法与结果

### 6.1 静态校验（283 项全部通过）

覆盖：表条目连续性与 `REG_SIZE` 自洽、`0x0103` 为首项、`0x0100=0x01` 为唯一 stream on、
`0x302d=0x00` 为末项、`0x3e03` 位于增益写入与 stream on 之前、分辨率/帧率不变式、
与原厂 SC500CS 表逐条一致性（仅允许多出 `0x3e03`）、AE 表字段映射、增益表 128 档全部落在表 2-4 合法行、
定序器常量与表索引一致、ID 常量正确。

### 6.2 动态仿真（iverilog 12.0，20 项全部通过）

新增 `sim/tb_uicfgcs520.v`：内置**开漏 I2C 从机模型**（上拉 + 标准 ACK 时序，对 `0x3107/0x3108`
返回 `0xEE`/`0x27`），抓取真实 I2C 字节流。实测结果：

| 观测项 | 实测值 |
| --- | --- |
| Sensor ID 读 | `0x3107=0xEE`、`0x3108=0x27` → `sensor_id=0xEE27`、`id_ok=1` |
| 配置写入条数 | **117 条**，索引 0..116 顺序无跳条无重复 |
| 软复位后延时 | **5.017 ms**（期望 5 ms） |
| stream on 后延时 | **10.017 ms**（期望 10 ms） |
| `O_iic_error` | `0`（全程无 NACK） |
| 分辨率/帧率 | `0x3208/09=0500`、`0x320a/0b=02d0`、VTS=`03e8` |
| AE 序列 | `3e00=00`、`3e01=7c`、`3e02=60` → 曝光 **1990 = 2×1000−10**；`3e08=1f`、`3e09=3f` → **15.750x**；`3e06=00`、`3e07=80` → 数字 **1.000x** |

## 7. 上板调试指引与待确认项

### 7.1 首次上电观察顺序

1. `hdmi_mixer` 的 `DEBUG_MODE=4` 状态码（`design_top_wrapper.v`）：

`HS_EQUALIZER` / `HS_VGA_GAIN` 本轮按 IP 默认 `0dB/0dB`（适配 480 Mbps）。Anlogic 未公开

### 7.4 板载 4 键接线（按键调曝光）

**背景**：原工程 `I_button` 只有 2 位，约束在 `N2`/`J14`，例化为 `.I_btn({I_button,2'b11})`。
这导致 `ae_set` 的 `I_btn[1:0]` 被硬接成"未按下"，**曝光按键是死代码**，4 个功能里只有增益 ±可用；
且 `N2`/`J14` 与开发板手册给出的板载按键引脚不符。

**开发板手册（新HX1P35A）第 18 节「4 组按键」原文**：

> 开发板板载了 4 个金属弹片型独立按键（KEY1~KEY4），**按键按下为低电平，松开为高电平**。
> 按键引脚分配：KEY1=**D5**、KEY2=**A9**、KEY3=**B9**、KEY4=**C7**

**本轮改动**：

| 文件 | 改动前 | 改动后 |
| --- | --- | --- |
| `constraints_source/pin.adc` | `I_button[0]=N2`、`I_button[1]=J14`（2 个） | `[0]=D5`、`[1]=A9`、`[2]=B9`、`[3]=C7`（4 个），全部 `PULLTYPE = PULLUP` |

**按键映射（低有效，按下=0）**：

| KEY2 | A9 | `[1]` | **曝光递增**（到 1990 为止） | 1 档 / ≈4.2 ms |

| KEY4 | C7 | `[3]` | 模拟增益递增（到 15.750x 为止） | 同上 |

**极性必须为 PULLUP**：`ae_set` 内部是 `r_button_0 <= ~I_btn`（低有效）。若这 4 个脚做成下拉或浮空到低，
空闲即被判为"一直按住"，由于 `if(r_button_1[2])` 的优先级高于 `else if(r_button_1[3])`，
`r_ag_set` 会从 144 自动降到 16 → `SC520GainTbl(16)` = `{0x3e08=0x03, 0x3e09=0x20}` = **模拟增益 1.000x**
→ **画面偏暗但颜色正常**（曝光仍是顶格 1990）。这正是"暗但颜色正常"的一个可复现成因，仿真已复现（见下）。

| --- | --- |

| KEY4 按下 → 增益递增 | 143 → 144 ✓ |
| 反例：4 脚全为低（模拟下拉） | 增益 144 → 142 自动递减 ✓（证明必须 PULLUP） |

**尚未处理（可选）**：`ae_set` 只对按键做了 2 级寄存（≈84 ns），没有真正消抖；不过步进速率已被

## 9. ISP 图像增强：接入黑电平校正与 Gamma

### 9.1 为什么需要

原链路（`isp_top.v`）只有 4 级，**没有任何色调处理**：

```
demosaic → data128_96 → awb → data_96bit_to_128bit → DDR → HDMI
```

且 `mipi_to_raw_converter.v:50` 把 RAW10 用 `{I_raw_tdata[9:2], ...}` 做 **>>2 线性截断**，
送出去的是 **8bit 线性**数据。显示器按 γ≈2.2 解释，线性 0.5（码值128）只显示成
0.5^2.2≈0.22（约码值60）——表现为**整体昏暗、暗部层次糊在一起（对比度不高）**。

工程里其实已经写好了三个增强模块，但**都没接**：

| 模块 | 原状态 |
| --- | --- |
| `axis_gamma_rgb96` | 定义在 `isp_top.v` 内部，**从未例化** |
| `BLC.v` | 独立文件，**不在 `.al` 编译列表里**（见 §9.7，直接引用会报 black box） |
| `image_correction.v` | 不在 `.al` 编译列表里；且实为裁剪模块，**不能接**（§9.3） |

### 9.2 接入后的链路

```
I_tdata(RAW10 x4, 40bit)
  ├─ blc_raw40       黑电平校正，减 15，下钳位到 0        ← 新增（内联在 isp_top.v）
  ├─ demosaic       BGGR，1280x720
  ├─ data128_96     128bit → 96bit RGB888
  ├─ awb            逐帧灰度世界白平衡
  ├─ axis_gamma_rgb96  16 段折线 γ≈0.7                  ← 新增
  └─ data_96bit_to_128bit → DDR → HDMI
```

**为什么 gamma 放在 `awb` 之后**：`awb` 用 R/G/B 的帧均值算增益（`in_r = G_avg/R_avg`）。
若把 gamma 放在它前面，gamma 会改变均值、被 awb 反向补偿掉一部分。正确顺序是
**先白平衡、后色调曲线**。

**为什么插入无 `tready` 的纯流水模块是安全的**：本 ISP 的 ready 链全部是
`assign I_tready = O_tready;` 的直通赋值、不参与任何逻辑判断
（`awb.v:381`、`bilinear_interpolation.v:910`，`zhenghe`/`line_buffer_demosaic` 连 ready 端口都没有），
顶层 `isp_top` 的 `O_tready` 更是一根**未被任何模块驱动**的悬空 wire
（`video_in` 没有 ready 输出）。整条通路是**纯 valid 驱动、无背压**，
因此插入 1 级延迟的纯流水不破坏握手；`tlast/tuser/tvalid/tdata` 同步延迟 1 拍，对齐关系不变。

### 9.3 为什么 `image_correction` 没接

**它的名字有误导性——它根本不是色彩校正，而是一个写死的窗口裁剪**：

```verilog
assign V_valid = (v_cnt >= 0) && (v_cnt <= 599);          // 只保留 600 行
assign H_valid = (h_cnt <= 255) && (h_cnt >= 0);          // 只保留前 256 拍
assign O_raw_tdata  = V_valid && H_valid ? I_raw_tdata_r : 0;   // 其余填 0
assign O_raw_tvalid = H_valid && V_valid && I_raw_tvalid_d;
assign O_raw_tlast  = V_valid && (h_cnt == 255) && I_raw_tvalid_d;
```

40bit = 4 像素/拍 ⇒ 256 拍 = **1024 px**；`v_cnt<=599` ⇒ **600 行**。
也就是它会把画面裁成 **1024×600** 并把其余像素清零/置为无效。
（旁证：早期 `uics500_cfg/uics500reg.v` 那张表正是 `0x3208/09=0x0400`(1024)、`0x320a/0b=0x0258`(600)，
说明这个模块是为那个 1024×600 模式写的。）
本工程 sensor 直出 1280×720，**接了会直接把图像裁坏**，故不接。

### 9.4 另外两个未接模块

| 模块 | 未接原因 |
| --- | --- |
| `auto_white_balance.v` | 它只负责**施加**外部给的 `I_r_gain/I_g_gain/I_b_gain`，本身不计算增益；工程里已有会算增益的 `awb`，无需它 |
| `raw8_to_rgb888.v` | 面向 **RAW8** sensor；本工程是 RAW10，接了反而错 |

### 9.5 可调参数

| 模块 | 位置 | 参数 | 含义 / 调法 |

| 黑电平校正 | `isp_top.v` `u_blc`（模块 `blc_raw40`） | `Black_level_offset_r0..r3` = `10'd15` | 10bit 域黑电平，约 15/1023。暗部仍发灰→加大；暗部死黑、细节丢失→减小 |

### 9.7 Black box 问题（HDL-7144 / HDL-8007）与最终做法

**现象**：第一次接入时 `isp_top.v` 直接例化厂商的 `BLC`，TD 综合报：

```
HDL-7144 CRITICAL-WARNING: instantiate unknown module BLC in .../isp_top.v(70)
HDL-8007 ERROR: BLC(Black_level_offset_r0=10'b01111,...) is a black box in .../isp_top.v(70)
```

**根因**：不是 IP 核问题（`BLC.v` 是 3 KB 普通 Verilog，`module BLC #(...)` 名字正确、
路径全英文），而是 **`BLC.v` 从来没进过 TD 工程源文件列表（`.al`）**，工具只看到例化、
找不到实现，于是当成黑盒。

而从外部往 `.al` 补条目**不可靠**——实测被连续覆盖两次：

| 时间 | 事件 |
| --- | --- |
| 14:29 前后 | 外部写入 BLC 条目成功（`<File>` 计数 58） |
| 14:29:27 | `.al` 被改写回 57 条，BLC 条目消失 |
| 14:33:14 | 再次写入成功（58 条） |
| 14:33:36 | 又被改写回 57 条 |

判断是 **TD 打开着本工程、保存时用内存里的旧文件列表覆盖了磁盘上的 `.al`**。

**最终做法（免疫覆盖）**：把黑电平校正**内联进 `isp_top.v`**，模块名 `blc_raw40`
（刻意不用 `BLC`，避免将来把 `BLC.v` 加进工程时模块重名冲突）：

| | 做法 | 是否要改 `.al` |
| --- | --- | --- |
| ~~旧~~ | 例化厂商 `BLC.v`，并往 `.al` 补文件条目 | **要**（会被覆盖 → black box） |
| **新** | 在 `isp_top.v` 末尾定义 `blc_raw40` 并例化 | **不要** ✅ |

`isp_top.v` 本来就在工程列表里（`CompileOrder 22`），所以这条路彻底不需要动工程文件。
厂商原本对 `axis_gamma_rgb96` / `axis_crop_rgb96` 用的就是这个办法——直接定义在
`isp_top.v` 内部，因此那两个模块从来不会报 black box。`BLC.v` 文件保留在磁盘上未使用。

> ⚠ **通用教训**：**TD 打开着工程时，不要从外部编辑 `.al`**（改完会被内存里的旧列表覆盖）。
> 若确实需要新增源文件，请用 TD GUI 的 `Add Source`，或先关闭 TD 再改。
> 同一个坑对 `pin.adc` 同样适用。

### 9.8 注释风格约定（避免踩坑）

不同文件类型的注释符不一样，用错会导致**注释被静默丢弃**或**语法错误**：

| 文件 | 类型 | 注释符 | 说明 |
| --- | --- | --- | --- |
| `*.adc`（`pin.adc`） | Tcl 风格约束 | **`#`** | ✅ 只能 `#`。TD 安装目录 30+ 个官方 `.adc` 样例里 `//` 出现 **0** 次 |
| `*.sdc` | Tcl | **`#`** | ✅ 只能 `#` |
| `*.al` | XML | `<!-- -->` | 未加注释 |
| `*.v` / `*.sv`（Verilog） | Verilog | **`//`** 与 `/* */` | ⚠ **不能改成 `#`**：`#` 是延时/参数覆盖运算符，`# 某某注释` 会直接语法错误 |
| `*.py`（`sim/`） | Python | **`#`** | ✅ |
| `*.md`（`doc/`） | Markdown | — | — |

之前 `pin.adc` 里的 4 行 `//` 注释就是这样被 TD 静默丢掉的，现已改为 `#`。

### 9.9 风险与回退
- **黑电平校正**：只减一个常数并下钳位，最坏情况是暗部变死黑 → 把 `10'd15` 减小即可。
- **Gamma**：纯查表映射，不改几何、不改时序；最坏情况是画面过亮/偏灰 → 调整曲线表。
- **代价**：各增加 1 拍流水延迟（对帧/行对齐无影响）；gamma 的 16 段折线需要约
  16×12 bit 的 LUT，资源开销很小（可用 ChipWatcher/综合报告确认）。
- **回退**：把 `isp_top.v` 中 `u_blc` 与 `u_gamma` 两个例化删除、并把 `demosaic` 输入改回
  `I_tdata/I_tlast/I_tvalid/I_tuser/I_tready`、把 `u_data_96bit_to_128bit` 的
  `I_96b_*` 改回 `awb_O_*` 即可。`blc_raw40` 是内联模块，**不需要动 `.al`**。

## 10. Sobel 边缘检测（128 位，二值化）

### 10.1 数据流与插入位置

按需求接在 **DDR2 写入之前**，落点是 gamma 之后、96→128bit 打包之前：

```
gamma(96bit, 4像素x24bit)
  → data96_128_pa     96->128，纯组合，4 x {8'h00,RGB}
  → sobel_edge_128    128 位，4 像素/拍            ← 本次新增
  → data128_96        128->96，纯组合
  → data_96bit_to_128bit（原有）
  → video_in → DDR2
```

两个宽度转换都是纯组合 `assign`（`data128_96` 是工程原有的，`data96_128_pa` 与它互逆），
**往返零延迟**，所以整条支路只增加 Sobel 自身的 5 拍流水，帧内拍数完全不变。

模块内部按需求分三级，与参考设计 `rgb_to_ycbcr.v` / `sosel_33_new.v` 一致：

| 级 | 模块 | 说明 |
| --- | --- | --- |
| 1 | `rgb_to_ycbcr_4` | `Y = (77R + 150G + 29B) >> 8`（BT.601 整数近似，与参考模块同一组系数） |
| 2 | `binarize_4` | `Y >= Y_THRESH` → 1，默认阈值 128 |
| 3 | `sobel_edge_128` | 二值图 3×3 Sobel，`gx`/`gy` ∈ [-4,4]，`|gx|+|gy| >= G_THRESH` 判为边缘 |

输出按需求改为 **24 位 0 / 24 位 1**：边缘 → `24'hFFFFFF`，非边缘 → `24'h000000`
（每个 32 位 lane 为 `{8'h00, 24'h000000 或 24'hFFFFFF}`）。

### 10.2 4 像素/拍下的 3×3 窗口

参考设计是 1 像素/拍、用两块 BRAM 做两行延迟。本工程是 **4 像素/拍**，
所以窗口一次要覆盖 3 行 × 6 列（4 个输出像素各需左右邻，共 6 列）。

- 每行把一拍 4 个像素打包成 **4 bit**，所以一行 1280 像素 = 320 个字
- 每行维护 3 拍滑窗 `{prev, w0, next}`（12 bit），合并成 6 位列窗口 `W[8:3]`
- 行延迟用 **两块 BRAM**，按行号奇偶分开放：
  - 行 N 写 `RAM_{N[0]}` 地址 `beat`
  - 行 N-1 读 `RAM_{~N[0]}` 地址 `beat+1`（预读一拍）
  - 行 N-2 读 `RAM_{ N[0]}` 地址 `beat+1`
  - `RAM_{N[0]}` 上"写 beat / 读 beat+1"落在双端口 RAM 的两个端口，互不冲突；
    且 `beat+1` 尚未被本行写覆盖，**所以 2 块 RAM 够用，不需要 3 bank**
- `beat+1` 预读让三行的 `next` 都在同一拍就绪，输出与输入天然对齐，无额外拍延迟

### 10.3 BRAM 而不是 LUTRAM

`sobel_line_ram` 直接例化安路原语 `PH1P_LOGIC_ERAM`，`IMPLEMENT("20K(FAST)")`
强制落在 20K block RAM，不用分布式 LUTRAM。

依据：TD 自己的 BRAM IP 实例用的位宽是 **32 / 33 / 96**（见
`blk_mem_gen_zhenghe` / `blk_mem_gen_demosaic` / `blk_mem_gen_awb_delay_signal`），
说明原语接受任意位宽——生成器界面里那份 `3;;6;;12;;24;;…` 只是 UI 预设，不是硬件限制。
本设计因此用 512×4、`REGMODE_B = "NOREG"`（读延迟 1 拍，与工程内两个 IP 实例一致）。

> 仿真时 iverilog 不认这个原语，需要一起编译 `sim/prim_ph1p_eram_sim.v`（行为模型）。
> 如果 TD 不接受直接例化，在 `sobel_edge_128.v` 文件头加 `` `define SOBEL_LINE_INFER ``
> 即可切成推断式 RAM 兜底（此时 TD 可能映射到 LUTRAM）。

### 10.4 边界处理（踩过的两个坑）

边界既不能补 0、也不能把无效字塞进流水链，否则会凭空多出假边缘：

| 边界 | 错误做法 | 现象 | 正确做法 |
| --- | --- | --- | --- |
| 行最右列 | 右邻补 0 | 白底最右列算出 `\|gx\|=4`，多一条竖线 | **复制**本拍最后一个像素 → 梯度 0 |
| 行最左列 | 左邻补 0 | 同上（白底最左列） | **复制**本拍第一个像素 |
| 行末→下一行 | 把行末的无效字替换后**写回移位链** | 该字顺链下流，污染下一行前两拍的 `w0`/`prev`，前两列出现假边缘 | 链里只走真实数据，**边界替换放到计算级组合完成** |
| 帧内前 2 行 | —— | 无法构成 3×3 窗口 | 输出全黑，但**拍数不变**（不能用 valid 门控，否则 DDR 帧布局错） |

另外：整幅图像相对输入**下移 1 行**（输出第 N 条行的位置对应 Sobel 的第 N-1 行），
最后一行自然取到上一行的结果，所以行数仍为 720。

### 10.5 可调参数

| 参数 | 位置 | 默认 | 说明 |
| --- | --- | --- | --- |
| `SOBEL_EN` | `isp_top` 参数 | 1 | 0 = 旁路，输出正常彩色图像，便于对比调试 |
| `SOBEL_Y_THRESH` | `isp_top` 参数 → `binarize_4` | 128 | Y 二值化阈值。调低→更多像素算"白"，边缘变密 |

### 10.7 风险与回退

- **时序**：Sobel 每拍要做 4 组 3×3 卷积（各 6 次加法）+ 两级 BRAM 读，
  路径比 gamma 长。若时序紧张，可在 S3 与 S4 之间插一级寄存，并把 `s4_*` 控制链多延一拍。
- **资源**：2 块 20K BRAM（实际每块只用 320×4 bit）+ 少量乘法器（RGB→Y 的 3 个常数乘法）。
- **回退**：把 `isp_top` 的 `SOBEL_EN` 改成 `1'b0` 重新综合即可（Sobel 逻辑会被优化掉）；
  彻底删除则去掉 `u_sob_pack`/`u_sobel`/`u_sob_unpack` 三个例化、`path_*` 三个 wire，
  并把 `u_data_96bit_to_128bit` 的 `I_96b_*` 改回 `gamma_O_*`。
- **`.al` 不需要动**：Sobel 的模块与 `blc_raw40` 一样内联在 `isp_top.v` 内
  （由 `sim/inline_sobel.py` 从 `sobel_edge_128.v` 生成），避免 black box。

## 11. 形态学：开运算 -> Sobel -> 闭运算（5 级流水）+ 运行期控制

### 11.1 数据流（按指定顺序）

```
二值化 ─► [win1] ─► 腐蚀 ─► [win2] ─► 膨胀 ─► [win3] ─► Sobel
       ─► [win4] ─► 膨胀 ─► [win5] ─► 腐蚀 ─► 24bit 0/1
       └──── 开运算 ────┘                  └──── 闭运算 ────┘
```

语义与之前的版本完全不同：

| 位置 | 运算 | 目的 |
| --- | --- | --- |
| Sobel **之前** | 开运算（先腐蚀后膨胀） | 去掉二值图里的孤立白点，让边缘更干净 |
| Sobel **之后** | 闭运算（先膨胀后腐蚀） | 对**边缘图**做闭运算 → 连接断裂的边缘线、补边缘缺口 |

### 11.2 为什么是 5 级而不是 3 级

一个 `bin_rowwin` 只能提供"某一幅图像"的 3x3 邻域，也就是**只能做一次 3x3 运算**：

| 运算 | 需要几次 3x3 | 需要几个窗口 |
| --- | --- | --- |
| 开运算 | 2 | 2 |
| Sobel | 1 | 1 |
| 闭运算 | 2 | 2 |
| **合计** | **5** | **5** |

只有"**单次**腐蚀"或"**单次**膨胀"才能借用已有窗口（那才是零缓存）；
"先腐蚀**再**膨胀"里的第二个运算看的是第一个运算的**结果**，必须多一个窗口。

### 11.3 资源与副作用

器件实测（改动前的报告）：`#eram 39/108 (36.11%)`、`#lut6 46.64%`、`#dsp 32/40`。
每个窗口用 2 块 ERAM（按行奇偶分开放），从 2 块增到 10 块：

| 项目 | 改动前 | 改动后 |
| --- | --- | --- |
| ERAM | 39 块 | 约 **47 块 / 108（43.5%）** |
| 流水延迟 | 1 行 | **5 行** |
| 帧内全黑行 | 前 3 + 后 3 | **前 5 + 后 5 = 10 行**（720 行损失 1.4%） |
| 逻辑 | —— | 4 个 9 输入 AND/OR 网络，约 160 LUT，不占 DSP |

后 5 行变黑是"输出槽位 i 对应最终结果第 i-5 行"的必然结果。
`MORPH3X3_EN = 0` 可让四个形态学步骤全部直通（延迟不变），便于上板 A/B 对比。

### 11.4 运行期控制（按键 + 拨码）

三个量**都只递增、到顶清零**（按住即连续步进，松手停在当前值）：

| 控制 | 引脚 | 作用 | 范围 / 步进 |
| --- | --- | --- | --- |
| **KEY1** `I_button[0]` | D5 | **曝光 `O_ae`** | 每次 **+64 半行**（+0.95 ms），到 2244（=2·VTS−10）回 **0** |
| **KEY2** `I_button[1]` | A9 | **边缘/梯度阈值 `G_THRESH`** | 每次 +1，走完 1..8 回 **0** |
| **KEY3** `I_button[2]` | B9 | **亮度二值化阈值 `Y_THRESH`** | 每次 +1，走完 0..255 回 **0** |
| **KEY4** `I_button[3]` | C7 | **未使用** | —— |
| **SW1** `I_sw1` | A4 | **原 RGB 彩图 / 二值结果 选择**：拨上(1)=二值/边缘图，拨下(0)=原彩图 | —— |

步进速率：曝光与边缘阈值用 `r_a8_tick`（8 × `r_ae_tick` ≈ 34 ms/档，曝光 36 档走完约 1.2 s）；
亮度阈值用 `r_ae_tick`（≈4.2 ms/档，0..255 走完约 1.1 s）。

> **按下瞬间可能吃掉一档**：按键同步（`r_button_0`→`r_button_1`）比 tick 的 1 拍脉冲慢 2 个周期，
> 若按下正好落在 tick 边沿附近，那一拍不会计数。所以"想看变化请按住 0.1 s 以上"，
> 别用轻点计数。`sim/tb_ae_set.v` 因此用"等到值变化"而非死数 tick 个数来断言。

**模拟增益不由按键控制**，固定 144（15.75× 上限）。注意：这个增益配合接近整帧的曝光，
在正常室内照明下**会过曝** —— 过曝会把图像推到二值化阈值附近，导致 Sobel 边缘图
大片翻黑白闪烁。遇到这种情况先按 KEY3 把 `Y_THRESH` 提到 200 上下、KEY2 把 `G_THRESH`
提到 4~8；若仍过曝，需要把 `ae_set.v` 里的 `r_ag_set` 从 144 降到 112（8×）或 80（4×）后重烧。

- 曝光与模拟增益**不再由按键控制**，固定 1990 / 144（最亮配置），
  所以 `isp_top` 里的 `SOBEL_Y_THRESH` 参数已改为运行期输入 `I_sobel_y_thresh[7:0]`。
- 二值化阈值作用在 **gamma 之后**的 Y 上，默认 128 等效"原始亮度 >= 95（满量程 37%）判为白"。
- 边缘阈值：二值图下 `|gx|+|gy| ∈ [0,8]`，所以 1..8 是有效范围；
  1 = 有梯度就算边缘（线最粗），4 = 只留干净边界，8 = 只留对角角点。
- SW1 拨上=1 与开发板手册第⑯节一致（"拨上为 1，拨下为 0"）。
- 顶层 `design_top_wrapper.v` 里 `S_sobel_en = I_sw1`，`isp_top` 用它在最后一级做二选一。

### 11.5 本轮修掉的一个真实 bug：行缓存预读地址越界

预读"下一拍"用的是 `beat + 1`。到行末 `beat = 319`（1280 像素时），
请求的是地址 **320** —— 越过本行末尾，读到的是**残留数据**；
而地址 **0 从来没被读过**。后果：

- 行内第 0 拍的字永远进不了移位链；
- 那个残留值顺着链流下去，成为下一行 beat0 的 `w0`、beat1 的 `prev`；
- 于是**每一行最左边两个像素的 3x3 窗口是错的**，左边缘凭空出现假边缘。

修复：行末把预读地址回绕到 0。

```verilog
wire [8:0] s2_raddr = s2_last ? 9'd0 : (s2_beat + 9'd1);
```

回绕后，行末读到的 `word(0)` 沿链正好成为下一行 beat0 的 `w0` / beat1 的 `prev`，天然正确。
仿真里可直接看到修复前后的差别：修复前图案 2 的裸 Sobel 输出是
`{4,7,10,12,13}`（错），修复后是 `{1,2,7,9,14,15}`（与手算一致）。

> 这个 bug 在之前两窗口的版本里也存在，上板表现是**图像左边缘有一条噪点/假边缘带**。

### 11.6 验证结果

| TB | 内容 | 结果 |
| --- | --- | --- |
| `sim/tb_sobel.v` | 16x30 小图，4 个图案 + 运行期双阈值 | **全部通过** |
| `sim/tb_sobel_pipeline.v` | 真实 `isp_top` 全链路端到端 | **通过（120/120 拍）** |
| `sim/tb_ae_set.v` | 4 键映射 / 钳位 / 拉低反例 | **9 项通过** |

两个形态学算子的决定性证据：

| 图案 | 现象 | 结论 |
| --- | --- | --- |
| 全黑底 + 单个白点 | 白像素 **0** | **开运算把孤立白点腐蚀掉了**（不做开运算会有 8 个） |
| 两个白块中间 1 像素黑缝 | 每行边缘列从 **6 列变 8 列** | **闭运算把第 8 列的缺口补上了** |

运行期阈值实测：`G_THRESH=9` → 整幅全黑，`G_THRESH=0` → 有效区整幅全白；
二值化阈值 128 时灰(200)算白、220 时算黑 → 证明阈值确实是运行期生效的。

### 11.7 回退

- 形态学：`sobel_edge_128.v` 里把 `MORPH3X3_EN` 改成 `1'b0`（四级全直通，延迟不变）。
- 只看彩图：SW1 拨下。
- 彻底删除：去掉 `u_win2`~`u_win5` 与 `u_morph2`/`u_morph4`/`u_morph5`，
  `u_win3` 的输入换回 `s2_bin`/`s2_valid`/...，`blank` 阈值从 5 改回 2，
  顶层 `I_sw1` 悬空即可。

## 12. 整帧频闪：工频闪烁的诊断与修复（方案 A 已实施）

### 12.1 现象与判据

画面**整个**以约 10 Hz 忽明忽暗，内容完整（没有撕裂/花屏/横带滚动），
拨 SW1 切彩图也照闪 —— 与 Sobel/形态学/DDR 都无关。

### 12.2 为什么是工频

PCLK = 96 MHz、HTS = 1600 → 1 行 = 16.667 µs；原 VTS = 1000 → 帧周期 16.667 ms，**正好 60.000 fps**。

| 光源 | 光周期 | 每帧相位推进 | 亮度图样重复 | 拍频 |
| --- | --- | --- | --- | --- |
| 灯以 100 Hz 闪（普通市电照明） | 10 ms | 16.667/10 = 1.667 周期 | 每 3 帧 | 20 Hz |
| 灯以 50 Hz 闪 | 20 ms | 16.667/20 = 0.833 周期 | 每 6 帧 | **10 Hz** |

**实测 10 Hz ⇒ 光周期 20 ms ⇒ 灯以 50 Hz 闪。**

> 先把曝光改成 1200 半行（10 ms = 20 ms 光周期的一半）试过一版，**仍然闪** ——
> 说明该灯的波形不满足"半个周期积分恒定"，必须用**整个**光周期。这条也否掉了
> "60 fps 下靠曝光解决"的路子：60 fps 帧长只有 16.67 ms，塞不下 20 ms 曝光。

### 12.3 消闪条件

**帧周期**或**曝光时间**必须是光周期（20 ms）的整数倍。

| 量 | 60 fps（原） | **50 fps（现）** |
| --- | --- | --- |
| 帧周期 | 16.667 ms = 0.833 个光周期 ✗ | **20.000 ms = 1 个光周期** ✓ |
| 帧长允许的最大曝光 | 16.58 ms ✗ 塞不下 20 ms | **19.917 ms ≈ 1 个光周期** ✓ |

50 fps 顺带同时满足 10 ms 光周期（20 ms = 2 × 10 ms），所以**对 100 Hz 和 50 Hz 两种灯都有效**。

### 12.4 已实施的改动（共 3 个数字）

| 位置 | 原值 | 新值 | 说明 |
| --- | --- | --- | --- |
| `uics520reg_720p60.v` 索引 28/29 `0x320e/0x320f` | `0x03e8` = 1000 | **`0x04b0` = 1200** | VTS → 50 fps |
| `uics520reg_720p60.v` 索引 94/95 `0x3e00/0x3e01` | `0x00` / `0x7c` = 1990 | **`0x00` / `0x95` = 2390** | 初始曝光同步到 2*VTS-10 |
| `ae_set.v` `r_ae_set`（初值 + 复位分支） | 1990 | **2390** | 运行期曝光 |

2390 半行 = 1195 行 × 16.667 µs = **19.917 ms**，是手册表 2-2 允许的上限 `2*VTS-10`。

**亮度**：19.917 ms 对比原 16.58 ms → **亮 1.20 倍**（之前试过的 10 ms 那版则是暗 1.66 倍，已废弃）。

### 12.5 为什么不用动别的地方

| 项 | 是否要改 | 原因 |
| --- | --- | --- |
| PCLK / HTS | ❌ | 都没动 → **MIPI 仍 480 Mbps/Lane** |
| SDC / D-PHY 参数 | ❌ | 速率没变 |
| 分辨率 | ❌ | 窗口仍是 1280×720 |
| FPGA 行/帧检查 | ❌ | `S_csi_data_length`（每行 800）和 `S_mipi_line_count`（720）都是**每行/每帧有效行**，与 VTS 无关 |
| ISP / Sobel / HDMI | ❌ | 只跟每行的像素数与行数有关 |
| 显示侧 | ❌ | 摄像头 50 fps、HDMI 60 Hz，靠既有 `rp` 机制自动重复帧 |

VTS 变大只是把**垂直消隐**从 280 行拉到 480 行（8 ms），顺带让 DDR 的读侧拿到更多无争用时间。

### 12.6 上板验证要点

1. 烧录后确认闪烁消失；若仍有，先看是否变成**别的**现象（横带/花屏 → 另查 §12.7）
2. 帧率应是 50 fps（可用示波器量 VSYNC，或看画面流畅度；30 fps 与 50 fps 肉眼可辨）

### 12.7 排除掉的其它嫌疑（都有代码依据）

| 嫌疑 | 为什么不是 |
| --- | --- |
| DDR2 读比写快 | 读指针 `rp = wp+2`（`video_in.v:121-138`），显示侧在**自己的 vsync** 上锁存整帧地址（`video_out.v:118-126`）→ 速率不匹配只造成**重复/跳过整帧**（顿挫），不会撕裂或忽明忽暗 |
| 形态学 / Sobel | 拨 SW1 切彩图照闪 → 无关 |
| DDR 读写争用 | 那会伴随**横向撕裂/局部花屏**，而本次画面完整、整体明暗 |
| MIPI 误码帧 | 表现为局部花屏而非整屏均匀明暗；**但** `design_top_wrapper.v:759` 把 `I_mipi_rx_error` 恒接 `1'b0`，坏帧保护实际是关的，建议接上真实错误信号 |

### 12.8 关于 1080p30（暂不做，记录备查）

**1080p30 本身不能消闪**：帧周期 33.333 ms，33.333/20 = 1.667 ✗，拍频仍是 10 Hz。
它能消闪的**唯一原因**是帧变长后能塞下 20 ms 曝光 —— 而 720p30 同样能塞下，代价小 10 倍。

若将来真要上 1080p，代价清单：

| # | 位置 | 改动 | 风险 |
| --- | --- | --- | --- |
| 1 | 传感器 I2C | 1080p30 全表 + **新 PLL 参数** | ⚠️ **最大坑**：SC500CS 手册没有 PLL 寄存器表（明说问 FAE），只能用厂商 SDK 的 `cfg_cs500.c` 试探 |
| 2 | MIPI 速率 | 变了 → SDC + PHY 均衡/增益/延时重调 | 高 |
| 3 | `isp_top` | demosaic / awb 的 `IMG_WIDTH/HEIGHT` → 1920/1080 | 中 |
| 4 | Sobel | `IMG_WIDTH` → 1920 → 每行 **480 拍**；行缓存 512 深**刚好够** | 低 |
| 5 | 顶层 | `S_csi_data_length != 16'h0320` → `16'h04B0`；`S_mipi_line_count != 720` → `1080` | 低 |
| 6 | HDMI | `uivtc` 1920×1080 时序 + PLL 74.25→148.5 MHz + `hdmi_mixer` | 中高（1.485 Gbps/lane，需确认 TMDS 能力） |
| 7 | DDR 帧缓存 | 间距 7,000,000 字节，1080p 需 6,220,800 → 够，余量降到 0.78 MB | 低 |

## 13. 整机升级到 1080p60

### 13.1 先说结论：频闪**没有**被解决

1080p60 的帧周期 = 1127 行 × 14.854 µs = **16.74 ms**，仍然 < 20 ms（50 Hz 照明光周期），
所以工频闪烁照旧。这是本轮"先不管频闪、先上 1080p60"的既定取舍。
要消闪必须让**帧周期或曝光**达到 20 ms 的整数倍 —— 1080p 下就是 VTS ≈ 2244（约 30 fps）。

### 13.2 传感器：换成厂商原厂 1080p60 表

来源：`04_MLK-CAM001-CS500\...\fpga_sdk\mipi_cs500\src\cfg_cs500.c` 的 `reg_cs500[]`，
由 `sim/gen_1080p60_table.py` 自动解析生成，**逐条一致**（116 条）。

| 项 | 720p60（原） | **1080p60（现）** |
| --- | --- | --- |
| 窗口 | 1280×720 | **1920×1080** |
| HTS `0x320c/d` | 1600 | **2852** |
| VTS `0x320e/f` | 1000 | **1127** |
| 像素时钟 | 96 MHz | **192 MHz** |
| MIPI `0x4837` | `0x42`（480 Mbps/Lane） | **`0x21`（960 Mbps/Lane）** |
| 帧率 | 60.0 fps | 192e6/(2852×1127) = **59.73 fps** |
| 曝光上限 2·VTS−10 | 1990 半行 | **2244 半行 = 16.667 ms** |

两处与原厂不同，均已记录：

1. **曝光初值收敛到手册上限**：厂商写 `0x3e01/0x3e02 = 0x8c/0x60`（= 2246，比 `2·VTS−10 = 2244` 大 2），
   本表改成 `0x8c/0x40`（= 2244）。
2. **去掉 `0x3e03 = 0x0b`**：该条是之前为 720p60 表加的 AGC 使能，厂商 1080p60 表里没有。
   既然本设计用手动 AE 控制曝光/增益，就与原厂保持一致，顺带排除一个可能的画面不稳来源。

序列结构与 720p60 表**不同**，定序器已相应改动：

| 项 | 720p60 表 | 1080p60 表 |
| --- | --- | --- |
| stream on 位置 | 索引 115（倒数第二条） | **索引 115（最后一条）** |
| stream on 之后 | 再写 `0x302d=0x00` | **无写入** |
| `0x302d` | 只在 stream on 前出现一次 | **出现两次**：索引 15 = `0x20`、索引 112 = `0x00` |

因此 `uicfgcs520.v` 新增 `POST_STREAM_WRITE = 1'b0`，关掉"stream on 后等 10 ms 再写"的分支。

> 表文件仍叫 `uics520reg_720p60.v`（文件名在 `.al` 里，不能随便加文件），
> 但里面现在有**两个模块**：旧的 `uics520reg_720p60`（保留供回退）与新的 `uics520reg_1080p60`。

### 13.4 PLL：为什么是 150 MHz 而不是 148.5 MHz

标准 1080p60 的像素时钟是 **148.5 MHz**，但：

```
VCO = 1500 MHz（C0: 1500/15=100M，C4: 1500/20=75M，C5: 1500/4=375M）
1500 / 148.5 = 10.101  -> 非整数
```

而且参考时钟是 50 MHz，整数分频下 VCO 只能是 50 的倍数，
`148.5 × k` 无论怎么取都无法整除 50 —— **148.5 MHz 在整数分频下不可达**。

采用的折中：**VCO 保持 1500 MHz 不变，只改输出分频**

| 时钟 | 原 | 现 | 分频 |
| --- | --- | --- | --- |
| CLK4（HDMI 像素） | 75 MHz | **150.000 MHz** | `CLKC4_DIV` 20 → **10** |
| CLK5（TMDS 串行） | 375 MHz | **750.000 MHz** | `CLKC5_DIV` 4 → **2** |
| CLK0 / CLK1 | 100 / 23.8095 MHz | **不变** | 不动 |

像素时钟比标准高 **+1.0%**，为此把 **HTOTAL 从 CEA 的 2200 加到 2223** 把刷新率拉回来：

| 量 | 标准 1080p60 | 本设计 | 偏差 |
| --- | --- | --- | --- |
| 像素时钟 | 148.5 MHz | 150.0 MHz | +1.0% |
| 行总长 | 2200 | 2223 | +1.0% |
| 行频 | 67.50 kHz | **67.48 kHz** | −0.03% |
| 场频 | 60.00 Hz | **59.98 Hz** | −0.03% |
| TMDS 速率 | 1.485 Gbps | 1.500 Gbps | +1.0% |

行频/场频几乎与标准一致，绝大多数显示器可以锁定。
**若某些显示器不接受**（表现为无信号/花屏），需要在 TD 的 PLL IP 里改用**小数分频**精确生成 148.5 MHz，
同时把 HTOTAL 改回 2200、HBP 改回 148、`uivtc` 的 H_FrameSize 改回 2200。

## 14. 算法观测点：用 SW2/SW3/SW4 定位横/竖线出自哪一级

### 14.1 为什么要这三个观测点

用户报告：1080p60 后画面出现过**匀速上升的横黑线**，且**彩图正常、只有二值/边沿图有问题**。
关键推理：

- 彩图通路 = `BLC -> demosaic -> AWB -> gamma -> 96->128 -> DDR -> HDMI`
- 二值通路 = 上面全部 **再加上 Sobel 模块**
- 两者共用 gamma 之前和 96->128 之后的所有环节

**既然彩图干净，问题就只可能在 Sobel 模块内部** —— 而 Sobel 模块里唯一"有状态"的东西
就是那些行缓存（`bin_rowwin` × 5）。所以需要在**行缓存之前/之间**插观测点。

### 14.2 三个观测点

| 拨码 | 引脚 | 观测点 | 行缓存 | 输出内容 |
| --- | --- | --- | --- | --- |
| **SW2** | **B4** | **二值化输出**（二值化之后、开运算之前） | **0 级** | 黑白二值图（未形态学） |
| **SW3** | **E11** | **Sobel 边沿输出**（Sobel 之后、闭运算之前） | **3 级** | 边缘黑白图（未闭运算） |
| **SW4** | **D11** | **Y 灰度**（RGB转YCbCr 的 Y 分量） | **0 级** | 真实灰阶（不是二值） |

优先级 **SW4 > SW3 > SW2**；三个都不拨 = 正常显示（此时由 SW1 决定彩图 or 开->Sobel->闭）。
每个观测点都用**自己的 valid/last/user**，所以各自显示的位置和行数都是正确的。

三个都拨上时为 SW4（Y 灰度）。

### 14.3 怎么用它定位

| 现象 | 结论 |
| --- | --- |
| **SW4（Y 灰度）就有横线** | 问题在 **Sobel 之前** —— MIPI/解拜耳/AWB/gamma。但注意此时彩图应该也会脏，若彩图干净则矛盾，要怀疑 96->128 打包 |
| SW4 干净、**SW2（二值化）有横线** | 问题在 **二值化** —— 阈值抖动/曝光不稳（阈值贴在饱和区时最明显） |
| SW2 干净、**SW3（边沿）有横线** | 问题在 **行缓存** —— `bin_rowwin` 的写地址/拍数/行计数，正是"拍数问题"的嫌疑区 |
| SW3 干净、**正常输出有横线** | 问题在 **闭运算那两级**（win4/win5） |

### 14.4 观测点与正常输出的差异（看的时候别误判）

| 项 | Y 灰度 (SW4) | 二值化 (SW2) | 边沿 (SW3) | 正常输出 |
| --- | --- | --- | --- | --- |
| 行消隐 | 无 | 无 | 无（消隐在更后面） | **前后各 5 行全黑** |
| 输出行数 | 全部 1080 行 | 全部 1080 行 | 全部 1080 行 | 首尾各 5 行黑 |
| 灰阶 | **真灰阶**（如灰 200 -> `0x00C8C8C8`） | 只有 `000000`/`FFFFFF` | 只有 `000000`/`FFFFFF` | 只有 `000000`/`FFFFFF` |
| 形态学 | 无 | **无**（这是重点） | 无闭运算 | 开 + 闭 |

**所以"观测点里出现的黑行"不一定等于"正常输出的黑行"** —— 正常输出前后各有 5 行是设计内消隐。

### 14.5 仿真自检（已加入 `sim/tb_sobel.v`）

| 用例 | 内容 | 结果 |
| --- | --- | --- |
| J | `dbg_sel=01` + 图案1（孤立白点）-> 白像素 = **1** | 证明二值化观测点确实是**开运算之前**（正常输出已被腐蚀掉，为 0） |
| K | `dbg_sel=11` + 图案3（灰 200）-> 出现 `0x00C8C8C8` 且**从未**出现 `0xFFFFFF` | 证明 Y 观测点是**真灰阶**（Y=(77+150+229)... 实际 (77+150+29)×200/256=200），不是二值 |
| L | `dbg_sel=10` + 图案0 -> 白像素 = **60 = 30 行 × 2 列** | 证明边沿观测点在**消隐之前**（全部 30 行都出边缘） |
